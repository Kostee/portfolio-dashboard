# Report Rules

## 1. Purpose

This document defines the calculation, aggregation and presentation rules for reports generated by Portfolio Dashboard.

The rules are intended to ensure that reports are:

- mathematically consistent,
- reproducible,
- based on clearly defined source data,
- transparent about missing information,
- visually consistent,
- suitable for desktop and mobile browsers,
- exportable as PNG files,
- independent from broker integrations.

The application generates reports in English.

The primary reporting currency is PLN.

## 2. Report categories

Portfolio Dashboard supports the following report groups.

### Weekly reports

- Added and sold instruments
- New assets by asset class

### Monthly reports

- Polish stocks portfolio structure
- International portfolio structure
- Assets by account
- Assets over time
- Asset class structure

### Performance reports

- Portfolio XIRR
- Nominal portfolio result
- Simple portfolio return

### Income reports

- Dividend summary by month
- Dividend summary by year
- Dividend summary by instrument
- Dividend summary by account
- Dividend summary by owner
- Dividend summary by provider

## 3. Shared report conventions

## 3.1 Report dates

Every report must have an explicit effective date or date range.

A report using a date range includes both boundary dates.

Example:

```text
2026-08-01 — 2026-08-03
```

includes events recorded on:

```text
2026-08-01
2026-08-02
2026-08-03
```

A one-day report displays one date instead of a duplicated range.

Example:

```text
03.08.2026
```

instead of:

```text
03.08.2026 — 03.08.2026
```

Internally, dates are stored and exported using ISO 8601:

```text
YYYY-MM-DD
```

Chart titles may use the existing reporting format:

```text
DD.MM.YYYY
```

## 3.2 Optional transaction time

Transaction date is mandatory.

Transaction time is optional.

When events share the same date:

1. events with a recorded time are ordered by time,
2. events without a recorded time are ordered by creation time,
3. a missing time remains unknown and must not be displayed as midnight.

For quantity calculations within the same date, all events effective on that date are included unless the user requests an intraday report.

Version 1 does not require intraday portfolio valuation reports.

## 3.3 Report generation timestamp

Every generated report stores:

- report type,
- selected effective date or date range,
- generation timestamp,
- source-data snapshot,
- report parameters,
- exchange rates used,
- asset-class names and colors used,
- report title,
- generated image path, when available.

The generation timestamp is not the same as the portfolio valuation date.

## 3.4 Language

Application labels and chart labels are displayed in English.

Examples:

```text
Added and sold instruments
New assets by asset class
Total purchases
Total sales
Net balance
External deposits
Portfolio value
Cumulative contributions
```

Deployment-specific data may contain user-defined owner and institution names.

## 3.5 Number formatting

Internal calculations use full stored decimal precision.

Rounding is applied only for presentation.

Default display rules:

```text
PLN, EUR and USD amounts     2 decimal places
Percentages                  1 decimal place by default
XIRR                         2 decimal places
Instrument quantities        up to 12 decimal places, trailing zeros removed
FX rates                      up to 6 decimal places when displayed
```

The default chart format uses:

- a space as the thousands separator,
- a dot as the decimal separator,
- an ISO currency code.

Examples:

```text
2 000.00 PLN
500.00 USD
50.002 EUR
0.125 DEMO
25.00%
```

Stored values must not be rounded before aggregation.

## 3.6 Signs

Report calculations use the following sign conventions.

```text
Buy                    positive in purchase charts
Sell                   negative in trade charts
External deposit       positive in contribution summaries
XIRR deposit           negative cash flow
XIRR terminal value    positive cash flow
Negative asset class   negative net contribution
```

Database monetary amounts may be stored as positive absolute values when their semantic direction is represented by the event type.

## 3.7 Source-data stability

A historical generated report must not silently change after:

- an instrument is renamed,
- an asset class is renamed,
- an asset-class color is changed,
- a transaction is edited,
- a valuation is updated,
- an exchange rate is changed.

The report stores a source-data snapshot and generation parameters.

When source data changes, the user may:

- keep the existing report,
- generate a new report,
- explicitly delete the old report.

## 3.8 Account display names

Accounts are displayed using:

```text
Owner · Provider · Account name
```

Example fictional format:

```text
Alex · DemoBroker · IKE
```

Reports must not hardcode real owners or providers.

## 3.9 Instrument aggregation

Unless a report explicitly states otherwise, the same instrument is aggregated across all accounts.

An instrument held on several accounts remains one instrument in portfolio-level reports.

Account-level detail remains available in:

- tooltips,
- supporting tables,
- the Holdings view,
- the Assets by account report.

## 3.10 Zero-value rows

Rows with:

```text
quantity = 0
```

are excluded from current holdings reports.

Rows with a non-zero quantity and zero unit valuation may be displayed only if zero is an intentional recorded valuation.

Missing valuation is not equivalent to a zero valuation.

## 4. Event inclusion matrix

Version 1 derives report behavior from event type.

No generic `include_in_report` flag is used.

| Event type | Weekly trades | Weekly deposits | Dividend reports | Current quantity | XIRR cash flow |
|---|---:|---:|---:|---:|---:|
| Buy | Yes | No | No | Increase | No |
| Sell | Yes | No | No | Decrease | No |
| External deposit | No | Yes | No | No change | Yes |
| Internal transfer | No | No | No | No change | No |
| Dividend | No | No | Yes | No change | No |
| FX conversion | No | No | No | No change | No |
| Position adjustment | No | No | No | Adjust | No |

Trade purchases and sales are internal portfolio activity.

They are not external XIRR cash flows.

Dividends remain inside the tracked portfolio unless the application later introduces an explicit withdrawal event.

## 5. Valuation rules

## 5.1 Quantity at a report date

For each account and instrument:

```text
initial quantity
+ buys effective on or before the report date
- sells effective on or before the report date
+ position adjustments effective on or before the report date
```

Only detailed events on or after the applicable baseline date are included.

## 5.2 Instrument valuation selection

For each non-zero holding, the report uses the latest instrument valuation effective on or before the report date.

Ordering:

```text
valuation date descending
valuation time descending
creation time descending
```

A valuation recorded after the selected report date must not be used automatically.

Example:

```text
Report date:       2026-08-03
Latest valuation:  2026-08-02
Next valuation:    2026-08-04
```

The report uses the valuation from:

```text
2026-08-02
```

## 5.3 Missing valuations

A current-value report must detect every non-zero holding without an applicable valuation.

By default, report generation is blocked if any required instrument valuation is missing.

The application should list:

- instrument,
- account,
- quantity,
- missing valuation date requirement.

Version 1 should not silently exclude unvalued holdings from portfolio totals.

A future version may allow an explicitly confirmed partial report.

## 5.4 Stale valuations

A valuation is stale when it is older than a configurable threshold.

Suggested default threshold:

```text
14 days
```

Stale valuations do not automatically block report generation.

The report-generation screen should show a warning containing:

- instrument,
- valuation date,
- valuation age.

The user may proceed after reviewing the warning.

## 5.5 Holding value

Value in the instrument currency:

```text
quantity × unit price
```

Value in PLN:

```text
quantity × unit price × applicable FX rate
```

For PLN-valued instruments:

```text
FX rate = 1
```

## 6. Exchange-rate rules

## 6.1 Historical trade values

Weekly transaction reports use the stored historical:

```text
amount_pln
```

from each trade.

They must not recalculate a historical trade using a later market FX rate.

## 6.2 Implied FX conversion rate

When a currency conversion is recorded, the application derives the rate from the exchanged amounts.

Example:

```text
500 PLN → 133.01 USD
```

Implied PLN per USD:

```text
500 / 133.01
```

A trade may reference the associated FX conversion.

When such a reference exists, the historical transaction PLN value may use the implied conversion rate.

## 6.3 Portfolio valuation FX rates

For current and monthly portfolio-value reports, the report requires an applicable rate for every non-PLN valuation currency.

Version 1 supports manually entered report rates.

The report-generation form should allow values such as:

```text
USD/PLN
EUR/PLN
```

If automatic NBP retrieval is later introduced:

- the retrieved value is shown before generation,
- the user may replace it manually,
- the source and date are stored,
- manual entry remains supported.

## 6.4 FX rate date

By default, a portfolio report uses the latest available FX rate effective on or before the report date.

A rate recorded after the report date must not be used automatically.

## 6.5 Missing FX rates

A portfolio-value report is blocked when:

- a non-PLN holding has a non-zero value,
- no applicable rate to PLN exists.

The application must identify the missing currency pair.

## 6.6 Report reproducibility

Every generated report stores the exact FX rates used.

A historical report must not change when the current FX rate changes.

## 7. Weekly report: Added and sold instruments

## 7.1 Purpose

This report summarizes instrument purchases and sales within a selected inclusive date range.

It reproduces the established horizontal-bar reporting style.

## 7.2 Required inputs

```text
period start
period end
```

Optional:

```text
custom title
```

The report derives total external deposits automatically from events within the selected period.

## 7.3 Included events

Included:

```text
buy trades
sell trades
```

Excluded:

```text
external deposits from the bars
internal transfers
dividends
FX conversions
position adjustments
valuation updates
```

External deposits are displayed separately as a period summary.

## 7.4 Aggregation

Trades are grouped by:

```text
instrument
```

across all accounts.

For each instrument:

```text
buy value  = sum(buy amount_pln)
sell value = sum(sell amount_pln)
net value  = buy value - sell value
```

The chart should preserve the direction of actual operations.

If an instrument was both bought and sold during the period, version 1 may display:

- one net bar, together with gross buy and sell values in the tooltip, or
- two directional bars for the same instrument.

The selected behavior must remain consistent within a report.

Preferred version 1 behavior:

```text
one net bar per instrument
```

A zero net value may still represent significant two-way trading.

When:

```text
gross buys > 0
and
gross sells > 0
and
net value = 0
```

the instrument should remain available in the supporting table even if no visible bar is produced.

## 7.5 Quantity label

Displayed quantity represents signed net quantity for the selected period:

```text
sum(buy quantity) - sum(sell quantity)
```

Preferred label format:

```text
Instrument [quantity]
```

Examples:

```text
Example Stock [3]
Example ETF [0.25]
Example Stock [-5]
```

If both buy and sell operations occurred and the net quantity would conceal useful information, a tooltip should show:

```text
Bought quantity
Sold quantity
Net quantity
```

## 7.6 Bar direction

```text
Purchases or positive net values    right of zero
Sales or negative net values        left of zero
```

A vertical zero line separates directions.

## 7.7 Sorting

Rows are sorted by absolute PLN value descending.

Tie-breakers:

1. absolute PLN value descending,
2. instrument display name ascending.

## 7.8 Colors

Every bar uses the current color assigned to the instrument’s asset class.

The exact colors used are stored in the generated report parameters.

## 7.9 Totals

The report displays:

```text
Total purchases
Total sales
Net balance
External deposits
```

Formulas:

```text
Total purchases = sum(all buy amount_pln)
Total sales     = sum(all sell amount_pln)
Net balance     = total purchases - total sales
External deposits = sum(external deposit amount_pln)
```

Total sales are displayed as a positive absolute summary amount.

The bars remain negative for sales.

## 7.10 Title and subtitle

Preferred one-day title:

```text
Added and sold instruments — 03.08.2026
```

Preferred date-range title:

```text
Added and sold instruments — 28.07.2026–03.08.2026
```

Preferred subtitle:

```text
Purchases = positive bars, sales = negative bars
```

The report should also display:

```text
External deposits: 2 000.00 PLN
```

either in the title area or summary footer.

## 7.11 Empty state

When the period contains no buy or sell events, the report displays:

```text
No purchases or sales in the selected period.
```

External deposits may still be displayed.

The application should not generate an empty misleading chart.

## 8. Weekly report: New assets by asset class

## 8.1 Purpose

This report summarizes the net effect of selected-period trades by asset class.

## 8.2 Included events

Included:

```text
buy trades
sell trades
```

Excluded:

```text
external deposits from class values
internal transfers
dividends
FX conversions
position adjustments
valuation updates
```

External deposits are displayed separately.

## 8.3 Asset-class net value

For each asset class:

```text
class net value
=
sum(buy amount_pln)
-
sum(sell amount_pln)
```

Overall net balance:

```text
sum(all class net values)
```

This must equal the net balance from the weekly Added and sold instruments report for the same period and source data.

## 8.4 Positive and negative classes

A positive class represents net acquisition.

A negative class represents net disposal.

Version 1:

- positive classes are displayed in the pie chart,
- negative classes are listed in a clear textual annotation,
- no hatched overlay is required.

Example note:

```text
Negative asset classes:
Polish Stocks: -1 000.00 PLN (-25.0%)
```

Version 2 may add:

- hatched overlay,
- graphical subtraction from the largest positive segment,
- other signed chart representations.

## 8.5 Percentage basis

Net-impact percentages are calculated against the overall net balance:

```text
class net value / overall net balance × 100%
```

This allows negative classes to have negative percentages.

Example:

```text
Semiconductors       88.8%
Global ETFs          37.9%
Bitcoin & Crypto     21.4%
Polish Stocks       -48.1%
Total               100.0%
```

Positive percentages may sum to more than 100% when negative classes exist.

This is intentional.

## 8.6 Pie geometry when negative classes exist

A conventional pie chart cannot display negative values.

In version 1:

- slice geometry uses positive class values only,
- positive slices are normalized against the sum of positive classes,
- displayed net-impact percentages may use the overall net balance,
- the report must explain the distinction.

Required explanatory note:

```text
Slice sizes show positive classes only.
Displayed percentages are calculated from the overall net balance.
```

The application may alternatively show positive-only slice percentages in the chart and net-impact percentages in the supporting table, provided both are clearly labeled.

The report must never present positive-only geometry as though it directly represented signed net percentages.

## 8.7 Non-positive overall balance

When:

```text
overall net balance <= 0
```

a conventional pie chart is misleading.

Version 1 should not render a pie chart in that situation.

Instead, display:

- a signed asset-class list or bar summary,
- total purchases,
- total sales,
- net balance,
- external deposits.

Suggested message:

```text
A pie chart is unavailable because the selected period has a non-positive net balance.
```

## 8.8 Title

Preferred title:

```text
New assets by asset class: 2 000.00 PLN — 03.08.2026
```

For a range:

```text
New assets by asset class: 2 000.00 PLN — 28.07.2026–03.08.2026
```

The amount in the title is the overall net balance.

## 8.9 External-deposit footer

Preferred footer:

```text
External deposits: 2 000.00 PLN; the remaining amount was financed using funds already available in portfolio accounts.
```

The footer must not imply that internal transfers are new capital.

## 9. Monthly report generation

## 9.1 Valuation date

Monthly reports use a user-selected valuation date.

The application must not assume that reports are always generated on a particular calendar day.

A recurring household workflow may use the second Saturday of a month, but this is not hardcoded into report calculations.

## 9.2 Required data

Before generation, the application validates:

- current quantities as of the valuation date,
- instrument valuations effective on or before that date,
- FX rates effective on or before that date,
- account configuration,
- asset-class configuration.

## 9.3 Monthly report package

A monthly generation action may create all five reports together.

The package stores shared parameters:

```text
valuation date
FX rates
asset-class colors
portfolio value
PPK value
generation timestamp
```

Each chart remains an independent generated report record.

## 10. Monthly report: Polish stocks portfolio structure

## 10.1 Purpose

Displays current Polish stock positions ranked by PLN value.

## 10.2 Default inclusion

The default report includes instruments assigned to:

```text
Polish Stocks
```

The selected asset class must be configurable because users may rename or replace the default class.

## 10.3 Position calculation

For each instrument:

```text
total quantity
=
sum(quantity across all accounts)
```

```text
total PLN value
=
sum(account-level PLN values)
```

Zero-quantity positions are excluded.

## 10.4 Ranking

Positions are sorted by total PLN value descending.

Tie-breaker:

```text
instrument name ascending
```

## 10.5 Display

Each position should show:

- instrument name,
- total quantity,
- PLN value,
- percentage of the report total.

Percentage:

```text
instrument PLN value / total Polish Stocks value × 100%
```

## 10.6 Multi-account ownership

When an instrument exists on multiple accounts, it remains one ranked instrument.

The detailed data view or tooltip should show:

- owner,
- provider,
- account,
- quantity,
- account-level value.

The chart may later support stacked account or owner segments, but this is not required for version 1.

## 10.7 Title

Preferred title:

```text
Polish stocks portfolio structure: 123 456.78 PLN — 03.08.2026
```

## 11. Monthly report: International portfolio structure

## 11.1 Purpose

Displays international holdings grouped by major asset class.

Default groups:

```text
Global ETFs
US REITs
Semiconductors
```

Additional international asset classes may be included later.

## 11.2 Inclusion

Version 1 uses a configurable list of asset classes selected for the report.

The report must not infer international status only from instrument currency.

A PLN-listed international ETF may still belong to Global ETFs.

## 11.3 Group totals

For each included asset class:

```text
class PLN value
=
sum(all included holding values in PLN)
```

Within each group, instruments are sorted by PLN value descending.

## 11.4 Display

The report should show:

- group name,
- group total,
- instrument name,
- quantity,
- value in original currency where useful,
- value in PLN,
- percentage of the full international report total.

## 11.5 Multiple instrument currencies

Original-currency amounts must not be added together across different currencies.

For example:

```text
EUR values and USD values remain separate
```

The full report total is calculated in PLN.

Optional title equivalents in EUR or USD are calculated from the full PLN total using the exact report FX rates.

They are currency equivalents, not sums of nominal instrument currencies.

## 11.6 Title

Preferred title:

```text
International portfolio structure
123 456.78 PLN — 03.08.2026
```

Optional equivalents:

```text
32 500.00 USD | 28 800.00 EUR | 123 456.78 PLN
```

The report parameters must identify the FX rates used for those equivalents.

## 12. Monthly report: Assets by account

## 12.1 Purpose

Displays total current portfolio value by account.

## 12.2 Inclusion

All active and historically relevant portfolio accounts with non-zero holdings are included.

PPK accounts are included.

Exchange channels are excluded because they are not portfolio accounts.

## 12.3 Account value

For each account:

```text
sum(all holding values in PLN)
```

## 12.4 Account labels

Preferred format:

```text
Owner · Provider · Account name
```

## 12.5 Ordering

Preferred default order:

1. configured account display order, when available,
2. owner display order,
3. account value descending,
4. account display name ascending.

A user-selectable descending-value order may be added later.

## 12.6 Display currency

Bar height uses PLN value.

When an account primarily uses another currency, the label may additionally show the original-currency equivalent.

Example:

```text
David · XTB · USD
12 345.67 USD
46 789.01 PLN
```

The PLN value remains authoritative for total portfolio reporting.

## 12.7 Title

Preferred title:

```text
Total portfolio value: 250 000.00 PLN — 03.08.2026
```

PPK is included in this amount.

## 13. Monthly report: Assets over time

## 13.1 Purpose

Displays the historical relationship between:

- total portfolio value,
- cumulative external contributions.

## 13.2 Historical sources

Before detailed tracking:

```text
portfolio_value_points
historical_external_deposits
```

After detailed tracking begins:

```text
calculated holdings values
external_deposit_events
```

Generated monthly portfolio value points may be stored for reproducibility.

## 13.3 Total portfolio value line

The total portfolio value line includes PPK.

## 13.4 Cumulative contributions line

Cumulative contributions include:

- historical external deposits,
- detailed external-deposit events.

They exclude:

- internal transfers,
- dividends,
- FX conversions,
- buys,
- sells,
- PPK contributions that are not tracked as external deposits.

## 13.5 Nominal difference

For each point:

```text
nominal difference
=
total portfolio value
-
cumulative tracked contributions
```

Because total portfolio value includes PPK while tracked contributions may exclude PPK contributions, the nominal difference is not presented as a pure investment return.

It may contain:

- market gains or losses,
- dividends retained in the portfolio,
- PPK value,
- employer or state PPK contributions,
- other untracked PPK inflows.

The chart should label it as:

```text
Nominal difference
```

rather than:

```text
Investment profit
```

## 13.6 Point selection

Version 1 uses explicitly stored historical valuation dates and generated monthly report dates.

It does not interpolate daily portfolio values.

## 13.7 Annual snapshot marker

A year-end or special annual snapshot may use a distinct marker.

This is a presentation rule, not a separate valuation formula.

## 13.8 Title

Preferred title:

```text
Portfolio value and cumulative contributions: 2025-11 → 2026-08
```

## 14. Monthly report: Asset class structure

## 14.1 Purpose

Displays current portfolio allocation across all active asset classes with non-zero value.

The report name must not assume exactly seven classes.

Preferred name:

```text
Asset class structure
```

## 14.2 Inclusion

All non-zero holdings are grouped by their instrument asset class.

PPK is included through instruments assigned to the PPK asset class.

## 14.3 Class value

```text
asset-class value
=
sum(all holding values in PLN assigned to that class)
```

## 14.4 Percentage

```text
asset-class value
/
total portfolio value
× 100%
```

Percentages must sum to 100%, subject to display rounding.

## 14.5 Ordering

Preferred ordering:

1. configured asset-class sort order,
2. descending class value as a secondary rule.

## 14.6 Colors

The current configured asset-class colors are used.

The exact colors are stored in the report parameters.

## 14.7 Small segments

When labels would overlap:

- use leader lines,
- move labels outside the chart,
- combine extremely small classes into `Other` only after explicit user confirmation.

Version 1 should prefer preserving every class over silently merging classes.

## 14.8 Title

Preferred title:

```text
Asset class structure: 250 000.00 PLN — 03.08.2026
```

## 15. Portfolio XIRR report

## 15.1 Purpose

Calculates one primary annualized portfolio return.

The user-facing report is titled:

```text
Portfolio XIRR
```

It does not need to state in the title that PPK is excluded.

## 15.2 Cash-flow sources

The XIRR vector contains:

1. historical external deposits before detailed tracking,
2. detailed external-deposit events after detailed tracking begins,
3. one terminal non-PPK portfolio value.

## 15.3 Cash-flow signs

```text
External deposit        negative
Terminal portfolio value positive
```

## 15.4 Excluded records

Excluded from XIRR cash flows:

```text
internal transfers
buy transactions
sell transactions
dividends
FX conversions
position adjustments
PPK contributions
PPK terminal value
```

## 15.5 Terminal date

The terminal date is the selected portfolio valuation date.

## 15.6 Terminal value

```text
terminal value
=
total portfolio value
-
value of all accounts where account_type = ppk
```

The main dashboard still displays total portfolio value including PPK.

## 15.7 Cash-flow verification

The report must allow the user to inspect the complete XIRR vector.

Displayed columns:

```text
Date
Cash-flow source
Amount in PLN
Included or excluded
Reason
```

## 15.8 Validation

The calculation is invalid when:

- no negative cash flow exists,
- no positive cash flow exists,
- terminal value is missing,
- the numerical solver does not converge.

The application must display a clear error rather than an invalid percentage.

## 15.9 Supporting values

The XIRR report may additionally display:

```text
Total portfolio value
PPK value
XIRR terminal value
Cumulative external contributions
Nominal result
Simple return
Valuation date
```

## 15.10 Simple return

For the non-PPK performance context:

```text
simple return
=
(terminal non-PPK value - cumulative external contributions)
/
cumulative external contributions
```

This metric is not annualized and does not account for contribution dates.

It must not replace XIRR.

## 16. Dividend reports

## 16.1 Purpose

Summarizes received dividend income.

Dividend reports are derived exclusively from dividend events.

## 16.2 Time grouping

Supported views:

```text
monthly
yearly
custom date range
```

## 16.3 Other grouping

Supported breakdowns:

```text
instrument
account
owner
provider
currency
```

## 16.4 Received amount

The primary amount is:

```text
amount_received
```

This is treated as the recorded received cash amount.

When withholding tax is recorded, the report may show:

```text
Received amount
Withholding tax
Arithmetic pre-tax total
```

Arithmetic pre-tax total:

```text
amount_received + withholding_tax_amount
```

This value must be labeled clearly and must not be presented as tax advice.

## 16.5 PLN conversion

When a stored `amount_pln` exists, PLN summaries use it.

When it does not exist:

- the report requires an applicable FX rate,
- the rate and source are displayed,
- the generated report stores the exact rate used.

## 16.6 Weekly reports

Dividends do not appear in:

- Added and sold instruments,
- New assets by asset class,
- external-deposit totals.

## 17. Report validation

## 17.1 Blocking errors

The following should block current-value report generation:

- missing instrument valuation for a non-zero holding,
- missing required FX rate,
- negative calculated holding without confirmed reconciliation,
- inconsistent workspace relationships,
- invalid report date,
- invalid date range,
- portfolio-value calculation failure.

## 17.2 Warnings

The following may allow generation after user review:

- stale instrument valuation,
- stale FX rate,
- zero-valued instrument,
- position adjustment in the selected period,
- historical point marked as reconstructed but not verified,
- unusually large trade or contribution,
- asset class with no assigned color.

## 17.3 No silent corrections

The report engine must not silently:

- change a negative holding to zero,
- replace a missing price with zero,
- use a future valuation,
- use a future FX rate,
- convert an internal transfer into an external deposit,
- include PPK in XIRR terminal value,
- omit a class because its label is difficult to place.

## 18. Report history

Every successfully generated report should appear in report history.

Report history displays:

```text
report type
effective date or period
generation timestamp
generated by
portfolio value or net balance
PNG availability
```

A historical report can be:

- opened,
- downloaded as PNG,
- regenerated as a new report,
- deleted after confirmation.

Regeneration creates a new record.

It does not overwrite the original report.

## 19. PNG export

## 19.1 General requirements

Generated charts should support PNG export.

The exported PNG must:

- have a white background,
- include the full title,
- include required legends,
- include required notes and totals,
- avoid clipped labels,
- remain readable outside the application,
- use the same source data as the stored report.

## 19.2 Suggested export dimensions

The web chart is responsive.

PNG export should use a stable high-resolution layout independent from the current phone screen size.

Suggested landscape export:

```text
1600 × 1000 pixels
```

Suggested square or pie-chart export:

```text
1400 × 1100 pixels
```

Exact dimensions may be refined in `CHART_STYLE.md`.

## 19.3 Mobile behavior

Mobile on-screen charts may simplify layout, but the exported PNG should use the full report layout.

The PNG must not be a low-resolution screenshot of the current mobile viewport.

## 20. Supporting data tables

Every chart should have an accessible supporting table.

The table should contain the values used to generate the chart.

This supports:

- validation,
- mobile readability,
- accessibility,
- troubleshooting,
- future CSV export,
- LLM-assisted analysis.

A chart is not the sole representation of financial information.

## 21. Cross-report consistency

Reports generated from the same period and source data must reconcile.

For a weekly period:

```text
Weekly trade net balance
=
sum(asset-class net values)
```

For a monthly valuation date:

```text
Total portfolio value
=
sum(account values)
=
sum(asset-class values)
=
sum(instrument values)
```

For XIRR:

```text
XIRR terminal value
=
total portfolio value
-
PPK account value
```

If totals do not reconcile within storage precision, report generation is blocked and the application displays a diagnostic error.

Display-rounding differences of a few smallest currency units may appear in labels.

The underlying source values must still reconcile.

## 22. Version 1 decisions

Version 1 uses:

- manual transaction entry,
- manual valuation updates,
- stored historical PLN trade values,
- manual report FX rates,
- optional future automatic NBP rates,
- positive-only weekly pie geometry,
- textual notes for negative asset classes,
- dynamic asset classes and colors,
- PPK included in displayed portfolio value,
- PPK excluded from XIRR,
- report source-data snapshots,
- PNG export,
- supporting data tables.

Version 1 does not require:

- a hatched negative-class overlay,
- live market prices,
- broker integration,
- tax calculations,
- intraday valuation reports,
- public report sharing,
- automatic classification based on ticker or exchange.
