# Chart Style

## 1. Purpose

This document defines the visual language and export standards for charts generated by Portfolio Dashboard.

The goal is to preserve the established reporting style:

- clean white backgrounds,
- restrained financial-report aesthetics,
- consistent asset-class colors,
- readable labels,
- transparent calculations,
- strong desktop and mobile usability,
- high-quality PNG exports.

The application does not need to reproduce historical Matplotlib charts pixel-for-pixel.

It should preserve their overall character, hierarchy, color logic and information density while remaining appropriate for a modern responsive web application.

## 2. General design principles

Charts should be:

- clear before decorative,
- readable without interaction,
- understandable outside the application after PNG export,
- visually consistent across reports,
- suitable for both desktop and mobile use,
- restrained rather than highly stylized,
- free from unnecessary animation or visual effects.

Charts should avoid:

- gradients,
- three-dimensional effects,
- shadows that reduce readability,
- glossy styling,
- excessive rounded decorations,
- saturated backgrounds,
- decorative patterns without semantic meaning,
- oversized titles,
- tiny labels,
- unnecessary legends.

The chart itself should remain the primary visual object.

## 3. Language

All application and report labels are displayed in English.

Example report names:

```text
Added and sold instruments
New assets by asset class
Polish stocks portfolio structure
International portfolio structure
Assets by account
Portfolio value and cumulative contributions
Asset class structure
Portfolio XIRR
Dividend summary
```

Institution names, instrument names and production owner names remain in their original form.

## 4. Background and canvas

Default chart background:

```text
#FFFFFF
```

All exported PNG files must use a solid white background.

Transparent PNG backgrounds are not used by default.

Chart containers inside the web application may use a subtle border or card background, but the exported chart canvas should remain white.

Suggested application card border:

```text
#E5E7EB
```

Suggested application page background:

```text
#F8FAFC
```

The chart image itself must not inherit the page background.

## 5. Typography

## 5.1 Font family

Preferred application and chart font stack:

```css
font-family:
  Inter,
  ui-sans-serif,
  system-ui,
  -apple-system,
  BlinkMacSystemFont,
  "Segoe UI",
  sans-serif;
```

The final chart must remain readable if the preferred font is unavailable.

PNG export must embed or correctly render the selected web font before image generation.

## 5.2 Typography hierarchy

Suggested desktop sizes:

```text
Report title             18–22 px
Report subtitle          13–15 px
Axis title               13–14 px
Axis labels              11–13 px
Data labels              11–13 px
Legend labels            11–13 px
Summary footer           11–13 px
Supporting note          10–12 px
```

Suggested mobile sizes:

```text
Report title             17–20 px
Report subtitle          12–14 px
Axis labels              10–12 px
Data labels              10–12 px
Legend labels            10–12 px
```

Titles should not dominate the chart.

A title should normally fit within:

```text
one line on desktop
two lines on mobile
```

Long titles may wrap naturally.

## 5.3 Font weight

Recommended weights:

```text
Main title               600
Section or group title   600
Primary labels           500
Regular labels           400
Supporting notes         400
Important totals         600
```

Avoid using bold text for every label.

## 5.4 Italics

Italics may be used for explanatory annotations.

Example:

```text
(negative net balance – textual annotation)
```

Italics should not be used for primary numeric labels.

## 6. Numeric formatting

Default chart formatting:

```text
Thousands separator      space
Decimal separator        dot
Currency notation        ISO code after value
Percentages              1 decimal place by default
XIRR                     2 decimal places
```

Examples:

```text
2 323.48 PLN
557.15 USD
57.22 EUR
37.8%
37.77%
```

Negative values:

```text
-1 117.70 PLN
-48.1%
```

The Unicode minus character may be used where rendering is reliable:

```text
−1 117.70 PLN
```

Instrument quantities should remove unnecessary trailing zeros.

Examples:

```text
3
0.25
0.125
0.002
```

## 7. Asset-class colors

The default asset-class palette reproduces the established portfolio-reporting colors.

```text
Polish Stocks          #3450A4
Global ETFs            #7E3FF2
Treasury Bonds         #8D99AE
Semiconductors         #24A6A8
Bitcoin & Crypto       #F2B000
US REITs               #E76F51
PPK Employment Plan    #C06C84
```

These are defaults only.

Users may:

- rename an asset class,
- change its color,
- add a new class,
- deactivate a class,
- reorder classes.

Historical generated reports preserve the exact colors used at generation time.

## 7.1 Color accessibility

Chart colors should remain distinguishable against white.

The application should warn when a selected color has insufficient contrast.

Color must not be the only method used to communicate:

- positive versus negative value,
- purchase versus sale,
- selected versus unselected state,
- warning versus error.

Direction, labels, signs and positioning must also communicate meaning.

## 7.2 Derived shades

A report may use lighter or darker shades of an asset-class color for:

- multiple owners,
- multiple accounts,
- nested position details.

Derived shades must remain visually connected to the base class color.

They should not replace the main asset-class color in portfolio-level reports.

#C56A11

```text
#6C7894
```

## 9. Axes and grids

## 9.1 General

Axes should remain subtle.

Axis lines should not visually compete with data.

Recommended grid behavior:

```text
Horizontal numeric grid      dashed, light gray
Vertical category grid       hidden or very subtle
Zero line                    solid, darker than grid
```

Suggested styles:

```css
grid:
  stroke: #D1D5DB;
  stroke-width: 1;
  stroke-dasharray: 4 4;

subtle-grid:
  stroke: #E5E7EB;
  stroke-width: 1;
  stroke-dasharray: 2 4;

zero-line:
  stroke: #6B7280;
  stroke-width: 1.25;
```

## 9.2 Axis labels

Axis labels should use whole or compact values when the chart is dense.

Examples:

```text
0 PLN
500 PLN
1 000 PLN
1 500 PLN
```

For very large totals, compact notation may be used on-screen:

```text
100k PLN
200k PLN
300k PLN
```

Exported PNG files should preferably retain complete values when space permits.

## 10. Tooltips

Interactive charts should provide tooltips.

Tooltips should contain enough information to verify the visible chart.

Typical tooltip content:

```text
Instrument
Asset class
Quantity
Purchase value
Sale value
Net value
Original currency value
PLN value
Percentage
Account breakdown
Valuation date
```

Tooltips must not be the only location where critical totals are shown.

Exported PNG files do not contain tooltips, so essential values must remain visible in labels, legends, summaries or supporting tables.

## 11. Legends

Legends should be used only when they improve readability.

Preferred legend positions:

```text
bottom
bottom-right
right side on wide desktop charts
```

Avoid legends that duplicate labels already shown directly beside chart elements.

Legend entries should preserve configured asset-class order.

Legend title may be:

```text
Asset class
```

A legend frame is normally unnecessary.

## 12. Data-label placement

Data labels should:

- remain outside crowded geometry when necessary,
- avoid overlapping,
- avoid clipping,
- use leader lines for pie and donut charts,
- remain aligned consistently,
- preserve readable distance from the plotted element.

When automatic placement fails, the export layout may apply deterministic manual offsets.

The export engine should allocate additional margins instead of shrinking labels excessively.

## 13. Responsive behavior

Charts must work in:

- desktop browsers,
- tablets,
- iPhone-sized screens,
- Android phones.

The responsive in-application view may differ from the exported PNG layout.

## 13.1 Desktop

Desktop charts may show:

- direct labels,
- complete legends,
- account details,
- wider supporting tables,
- full titles.

## 13.2 Mobile

Mobile charts may:

- wrap titles,
- move legends below the chart,
- reduce visible axis ticks,
- use horizontal scrolling for dense categories,
- collapse secondary annotations,
- provide a supporting table beneath the chart,
- switch from direct labels to tooltip-first interaction.

Mobile charts must not:

- hide core totals,
- crop labels,
- replace missing labels with unlabeled colors,
- force unreadably small text.

## 13.3 Export layout

PNG export uses a fixed high-resolution layout independent from the current viewport.

A chart exported from an iPhone should match the quality of a chart exported from a desktop browser.

## 14. Animation

Charts may use a short entrance animation inside the application.

Recommended maximum duration:

```text
300 ms
```

Animations should:

- be subtle,
- be disabled for PNG export,
- respect reduced-motion accessibility preferences,
- never delay report verification.

Animated transitions are optional, not required.

## 15. Weekly chart: Added and sold instruments

## 15.1 Chart type

Horizontal signed bar chart.

Purchases extend right from zero.

Sales extend left from zero.

The chart should visually resemble the established weekly Matplotlib report.

## 15.2 Title

One-day format:

```text
Added and sold instruments — 03.08.2026
```

Date-range format:

```text
Added and sold instruments — 28.07.2026–03.08.2026
```

Required title-area or directly adjacent summary:

```text
External deposits: 2 000.00 PLN
```

Preferred subtitle:

```text
Purchases = positive bars, sales = negative bars
```

The selected period and external-deposit total must be visible without opening a tooltip.

## 15.3 Categories

Each row represents one instrument aggregated across accounts.

Preferred label:

```text
Instrument [signed net quantity]
```

Examples:

```text
Example Stock [3]
Example REIT [-5]
Example Semiconductor [0.25]
```

When both buys and sells occurred, the supporting table and tooltip should show gross quantities separately.

## 15.4 Bar appearance

Recommended:

```text
Bar height                60–70% of category step
Corner radius             0–3 px
Stroke                    none
Opacity                   100%
```

Bars use asset-class colors.

Do not use gradients.

## 15.5 Direction and baseline

A vertical zero line is mandatory.

Suggested zero-line style:

```text
color                     #6B7280
width                     1.25 px
```

Positive values:

```text
right side
```

Negative values:

```text
left side
```

## 15.6 Sorting

Sort by absolute PLN value descending.

Largest activity appears at the top.

## 15.7 Value labels

Value labels appear near the end of each bar.

Positive labels:

```text
outside or just inside the right bar end
```

Negative labels:

```text
outside or just inside the left bar end
```

Example:

```text
615.38 PLN
-1 735.60 PLN
```

Labels should remain dark neutral text unless white text is required inside a sufficiently dark bar.

## 15.8 Axis title

Preferred:

```text
Transaction value (PLN)
```

## 15.9 Summary footer

Required values:

```text
Total purchases
Total sales
Net balance
External deposits
```

Preferred single-line desktop format:

```text
Purchases: 5 879.18 PLN | Sales: 3 555.70 PLN | Net balance: 2 323.48 PLN | External deposits: 2 000.00 PLN
```

On mobile, the summary may wrap into two rows.

Total sales are shown as a positive absolute amount in the summary.

## 15.10 Empty state

When no purchases or sales exist:

```text
No purchases or sales in the selected period.
```

The external-deposit total may still be displayed.

## 15.11 Suggested export size

```text
1600 × 1000 px
```

The height may increase when many instruments exist.

The export should never compress dozens of categories into unreadable rows.

## 16. Weekly chart: New assets by asset class

## 16.1 Version 1 chart type

Pie or donut chart displaying positive asset classes.

Negative asset classes are displayed as a textual annotation.

The version 1 chart does not require a hatched overlay.

## 16.2 Title

One-day format:

```text
New assets by asset class: 2 323.48 PLN — 03.08.2026
```

Date-range format:

```text
New assets by asset class: 2 323.48 PLN — 28.07.2026–03.08.2026
```

The value in the title is the signed overall net balance.

## 16.3 Start angle

The first slice begins at:

```text
12 o’clock
```

Preferred direction:

```text
clockwise
```

The configured asset-class order should determine slice order unless a report explicitly uses descending value order.

## 16.4 Positive slices

Positive asset classes use their configured colors.

Slice geometry is calculated from positive values only.

Each positive label should display:

```text
Asset class
Amount in PLN
Percentage
```

Example:

```text
Semiconductors
2 062.79 PLN (88.8%)
```

The displayed percentage may represent net-impact percentage based on the overall net balance.

When this differs from slice geometry, the chart must include an explanatory note.

## 16.5 Negative classes

Version 1 displays negative classes as text outside or below the chart.

Example:

```text
Negative asset classes:
Polish Stocks: -1 117.70 PLN (-48.1%)
```

The annotation:

- uses black or dark neutral text,
- has no surrounding rectangle,
- may use italics for explanatory text,
- should not appear as a fourth positive pie slice.

Required explanation when percentages use net balance:

```text
(Slice sizes show positive classes only.
Percentages are calculated from the overall net balance.)
```

## 16.6 Version 2 overlay

A later version may display negative classes through a hatched overlay.

Preferred established style:

- apply diagonal hatching over part of the largest positive slice,
- use the negative class color for the hatch,
- keep the underlying positive slice visible,
- place the negative-class label separately,
- show a negative amount and negative percentage,
- explain the overlay in italic text,
- avoid a rectangular label frame.

Version 2 explanatory text example:

```text
(negative net balance
– hatched overlay)
```

The overlay must never change the underlying source values.

## 16.7 Non-positive net balance

When the overall net balance is zero or negative, do not render a pie chart.

Use a signed horizontal bar summary instead.

## 16.8 Footer

Preferred:

```text
External deposits: 2 000.00 PLN; the remaining amount was financed using funds already available in portfolio accounts.
```

## 16.9 Suggested export size

```text
1400 × 1100 px
```

Additional width may be used when multiple annotations are required.

## 18. Monthly chart: International portfolio structure

## 18.1 Chart type

Grouped horizontal bar report separated into asset-class sections.

Default sections:

```text
Global ETFs
US REITs
Semiconductors
```

Additional configured international classes may appear.

## 18.2 Title

Preferred two-line format:

```text
International portfolio structure
32 500.00 USD | 28 800.00 EUR | 123 456.78 PLN — 03.08.2026
```

Currency equivalents are calculated from the full PLN total.

They are not nominal sums of mixed instrument currencies.

## 18.3 Section headers

Each section header should show:

```text
Asset-class name
Section total
```

For mixed currencies, original-currency totals remain separated.

Example:

```text
Global ETFs — 8 100.00 EUR | 2 500.00 USD
```

## 18.4 Bar colors

Each section uses its asset-class color.

Preferred defaults:

```text
Global ETFs        #7E3FF2
US REITs           #E76F51
Semiconductors     #24A6A8
```

Bars within a section should use one consistent class color unless account distinctions are intentionally introduced.

## 18.5 Instrument labels

Preferred:

```text
Instrument name [quantity]
```

The main chart should prefer readable names over raw tickers.

Tickers may appear in tooltips or supporting tables.

## 18.6 Value labels

Display original-currency value where useful.

Example:

```text
1 250.00 USD
```

PLN value should remain available in the tooltip and supporting table.

## 18.7 Section separation

Sections may be separated using:

- additional vertical spacing,
- subtle divider lines,
- section header labels.

Avoid enclosing each section in a heavy box.

## 18.8 Suggested export size

```text
1700 × 1300 px
```

Height should adapt to the number of positions.

## 19. Monthly chart: Assets by account

## 19.1 Chart type

Vertical bar chart.

## 19.2 Title

```text
Total portfolio value: 371 321.00 PLN — 03.08.2026
```

PPK is included.

## 19.3 Account labels

Preferred:

```text
Owner · Provider · Account name
```

Labels may rotate approximately:

```text
20–30 degrees
```

when space is limited.

Mobile may use a horizontal bar chart instead.

## 19.4 Bar colors

Colors may distinguish:

- owner,
- account type,
- provider.

Preferred default for version 1:

- use stable account colors derived from account type or owner,
- preserve the same account color between reports,
- avoid using asset-class colors because an account may contain multiple classes.

Suggested historical palette:

```text
Bonds                     #8D99AE
Owner A IKE               #2B55CF
Owner A IKZE              #467FDF
Owner A foreign account   #5E95DD
Owner A PPK               #7B7FE6
Owner B IKE               #117F58
Owner B IKZE              #1FB983
Owner B PPK               #91D8A5
Bitcoin account           #F2AF00
```

Production owner names must not be hardcoded in the public codebase.

The final palette should be generated or configured from account metadata.

## 19.5 Labels above bars

Display:

```text
Account value
Percentage of total portfolio
```

Example:

```text
46 789.01 PLN
12.6%
```

The amount should sit closer to the bar.

The percentage should appear slightly higher to create a clear visual hierarchy.

## 19.6 Foreign-currency account label

```text
12 345.67 USD
```

while bar height remains based on PLN value.

## 19.7 Axis title

```text

```

very subtle

1600 × 1000 px

## 21. Monthly chart: Asset class structure

Pie or donut chart.

The report name is dynamic and does not assume exactly seven classes.

## 21.2 Title

```text
Asset class structure: 371 321.00 PLN — 03.08.2026
```

## 21.3 Slice ordering

Preferred ordering:

```text
configured asset-class sort order
```

Alternative:

```text
descending value
```

The selected rule must be stored in report parameters.

## 21.4 Labels

Each class label should show:

```text
Asset class
PLN value
Percentage
```

Example:

```text
Global ETFs
84 500.00 PLN (22.8%)
```

Labels should preferably sit outside the pie with leader lines.

## 21.5 Small slices

For small slices:

- move labels farther from the pie,
- use leader lines,
- alternate left and right label columns,
- increase export dimensions,
- preserve all active classes.

Do not silently combine slices into `Other`.

Combining into `Other` requires explicit user confirmation.

## 21.6 Donut center

If a donut layout is used, the center may display:

```text
Total portfolio
371 321.00 PLN
```

This is optional.

## 21.7 Suggested export size

```text
1400 × 1100 px
```

## 22. Portfolio XIRR presentation

## 22.1 Primary display

The main XIRR result should be prominent but not oversized.

Example:

```text
Portfolio XIRR
37.77%
```

## 22.2 Supporting metrics

Display:

```text
Total portfolio value
PPK value
XIRR terminal value
Cumulative external contributions
Nominal result
Simple return
Valuation date
```

The normal user-facing label remains:

```text
Portfolio XIRR
```

The interface does not need to add `excluding PPK` to the main title.

The cash-flow explanation should clarify the methodology.

## 22.3 Cash-flow table

The XIRR screen should provide a table containing:

```text
Date
Source
Amount
Inclusion status
Reason
```

Included cash flows should be visually distinguishable from excluded reference rows.

## 22.4 Error state

When XIRR cannot be calculated, show a clear message.

Example:

```text
XIRR could not be calculated because the cash-flow vector does not contain both positive and negative values.
```

Do not show:

```text
NaN
Infinity
0.00%
```

as a fallback.

## 23. Dividend charts

## 23.1 Monthly dividend summary

Preferred chart:

```text
vertical bars by month
```

## 23.2 Yearly dividend summary

Preferred chart:

```text
vertical bars by year
```

## 23.3 Breakdown by instrument or account

Preferred charts:

```text
horizontal ranking bars
```

## 23.4 Currency handling

When dividend values are mixed across currencies:

- display PLN totals using stored or selected rates,
- expose original currencies in tooltips,
- store exact rates in report parameters.

## 23.5 Colors

Dividend reports may use:

- instrument asset-class colors,
- account colors,
- one neutral income color.

The legend and title must make the selected grouping clear.

## 24. Supporting tables

Every chart must have a supporting data table.

Table styling should use:

- white background,
- subtle borders,
- right-aligned numeric columns,
- left-aligned labels,
- sortable columns where useful,
- sticky headers for long tables,
- horizontal scrolling on mobile.

Tables should support exact-value verification.

Charts should not be the sole presentation of financial data.

## 25. Accessibility

Charts should support:

- keyboard navigation where provided by the chart library,
- screen-reader descriptions,
- high-contrast text,
- readable focus states,
- reduced-motion preferences,
- supporting data tables,
- semantic report titles.

Every chart should have an accessible text summary.

Example:

```text
This chart shows five purchased instruments and two sold instruments between 28 July and 3 August 2026. Total purchases were 5 879.18 PLN, total sales were 3 555.70 PLN and the net balance was 2 323.48 PLN.
```

## 26. PNG export rules

PNG export must:

- use a white background,
- use high-resolution fixed dimensions,
- wait for fonts to finish loading,
- disable animations,
- include the full title,
- include required notes,
- include totals,
- include legends where required,
- prevent clipped labels,
- preserve configured colors,
- use stored report source data,
- work independently from the current screen size.

Suggested approach:

```text
render an export-specific chart layout
rather than capture the visible mobile viewport
```

The exported image should include small padding around all edges.

Suggested minimum outer padding:

```text
32–48 px
```

## 27. Report-history preview

Report-history thumbnails may use simplified layouts.

Thumbnails do not replace the full chart.

A report card should show:

```text
Report type
Effective date or period
Generation date
Primary total
Thumbnail
PNG status
```

## 28. Chart implementation guidance

The initial implementation should prefer:

- SVG-based chart rendering,
- deterministic layouts,
- reusable chart components,
- export-specific rendering,
- library-independent domain calculations.

The charting library must not contain financial business logic.

Business calculations should produce a report-data object.

The visual component should only render that object.

Conceptual separation:

```text
portfolio data
→ report calculation service
→ immutable report-data object
→ responsive chart component
→ PNG export renderer
```

This makes it possible to replace the charting library later without rewriting portfolio calculations.

## 29. Version 1 visual scope

Version 1 should deliver:

- white report backgrounds,
- English labels,
- configurable asset-class colors,
- responsive charts,
- weekly signed horizontal bars,
- weekly positive-only asset-class pie with negative textual notes,
- Polish-stock ranking bars,
- international grouped bars,
- assets-by-account bars,
- two-line historical chart,
- asset-class pie or donut,
- XIRR metric presentation,
- dividend summary charts,
- supporting tables,
- PNG export.

Version 1 does not require:

- pixel-perfect Matplotlib reproduction,
- custom canvas rendering,
- hatched negative-class overlay,
- advanced collision-avoidance algorithms,
- animated storytelling,
- three-dimensional charts,
- gradient fills.

## 30. Version 2 visual candidates

Possible later improvements:

- hatched negative asset-class overlay,
- manually adjustable label positions,
- account-stacked instrument bars,
- owner-stacked Polish-stock bars,
